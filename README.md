# Курсовая работа

## Описание
В рамках курсовой работы была разработана информационная система потоковой обработки данных. Разрабатываемая система будет моделировать снятие информации с датчиков активности пользователей и анализ этой информации. В рамках этой системы потоковыми данными будут сообщения, периодически приходящие с пользовательских устройств и содержащие информацию об их координатах по трем осям (в дециметрах) и пульсе.

### Результаты обработки данных
Обработка получаемых потоковых данных в качестве результатов имеет подсчет среднего пульса пользователя в определенном временном окне, подсчет перемещения пользователя за определенное временное окно и оценку загруженности раздичных координатных областей.


### Толерантность к запаздыванию обработки
Результаты обработки данных не будут использоваться для принятия критически важных, не терпящих задержки решений, поэтому запаздывание обработки в пределах нескольких минут будет приемлемым. 


### Толерантность к потере данных
Содержимое каждого сообщения полностью отражает состояние клиента в определенный момент, таким образом, каждое следующее сообщение не связано с предыдущим и является самодостаточным. В связи с этим потери примерно до 20 процентов сообщений смогут снизить точность анализа, но не приведут к отказу системы. В связи с небольшой ценностью каждого отдельно взятого сообщения будет разумным выбрать семантику обработки "не более одного раза".


## Отдельные подсистемы
Функционирование системы обеспечивается за счет работы нескольких отдельных компонентов:
- **Предоставление иcходных данных.** Предполагается, что в реальных условиях данные будут предоставляться фитнес-браслетами реальных пользователей. В рамках работы пользователи и их активность создавались искуственно с помощью программного эмулятора. Каждый "браслет" раз в 5 секунд отправляет по протоколу TCP данные серверу.
- **TCP-сервер.** Задачей этого компонента является сбор сообщений от пользователей по протоколу TCP и помещение их содержимого в виде сообщений с ключами  в соответствующие топики Kafka.
- **Звено анализа данных.** На этом этапе с помощью Apache Flink осуществляется потоковая аналитическая обработка поступающих в топики Kafka сообщений. На основе получаемых сообщений производятся оконные вычисления скорости и пульса, а также поиск наиболее загруженных районов карты. Результаты обработки будут помещаться в другие топики Kafka.
- **Потоковое API.** Этот компонент получает из топиков Kafka результаты анализа данных в виде потока и направляет эти данные клиентским приложениям, подключенным к серверу.
- **Клиентское приложение.** Клиентское приложение является заключительным звеном в цепи подсистем, составляющих разрабатываемую информационную систему. Оно представляет собой графическое приложение, отображающее на координатвной сетке наиболее загруженные квадраты и, в случае предоставления id пользователя, чертит на карте его маршрут по точкам.
 
  
## Предоставление иcходных данных
В директории "generator" в файле client.py содержится код, периодически отсылающий сообщения о статусе клиента. В этом файле также содержится логика имитации активности пользователей. В файлах из директории user1 приведены файлы примеры, содержащие информацию о пользователе и текущую команду - дейстиве, которое "пользователь" выполняет в текущий момент. Активность пользователя можно менять в режиме реального времени, перезаписывая команду и направление в файле current_action.txt.

Доступные команды:
rest, walk, easy_run, hard_run, cycle, drive, fly

направления:

forward, back, right, left, up, down

Файл generate_activity.py инициирует активизацию одновременно нескольких пользователей, чтобы модель системы была больше похожа на реальную.


## TCP-сервер 
Код TCP-сервера, являющегося по совместительству producer-ом Kafka, представлен в директории data_collection_unit. Для передачи данных серверу по TCP объекты, содержащие информацию о координатах пользователя по трем осям, текущий пульс, id пользователя и временную метку генерации сообщения, сериализуются в байты на стороне приложения "фитнес-браслета" и десериализуются на стороне TCP-сервера. ## Звено анализа данных
Входными данными для этого компонента системы являются потоки сообщений из топиков "location" и "pulse" в Kafka. Специальным программным обеспечением, используемым для осуществления вычислений над потоковыми данными, является Apache Flink. Для взаимодействия с ним нужно запустить кластер Flink. Этот кластер предназначен для выполнения загружаемых в него пользователями в формате jar-архива задач. В целях разработки не обязательно запускать настоящий кластер Flink - java-пакеты для работы с Flink позволяют среде разработки автоматически создавать микрокластеры при запуске программы. При запуске такого кластера из среды разработки используются зависимости Flink. При упаковке задачи в jar-архив в него не добавляются эти зависимости, так как их в runtime предоставит кластер Flink, в котором задача будет исполнена. 

Задача в Flink определяется, в первую очередь, источником данных для нее. В данном случае источниками являются топики Kafka.

```
KafkaSource<LocationRecord> location_source = KafkaSource.<LocationRecord>builder()
				.setBootstrapServers("127.0.0.1:9092")
				.setTopics("location")
				.setStartingOffsets(OffsetsInitializer.latest())
				.setDeserializer(new LocationRecord())
				.build();
```

При считывании сообщений, значения которых не являются базовыми типами, такими как Integer, Long или String, необходимо предоставление определенного пользователем десериализатора, восстанавливающего из байтов полученного сообщения объект пользовательского типа.


```
public class LocationRecord implements KafkaRecordDeserializationSchema<LocationRecord>, KafkaRecordSerializationSchema<LocationRecord> {

    ...

    @Override
    public void deserialize(ConsumerRecord<byte[], byte[]> message, Collector<LocationRecord> out) {

        ByteBuffer key = ByteBuffer.wrap(message.key()); // big-endian by default
        ByteBuffer value = ByteBuffer.wrap(message.value()); // big-endian by default

        var res = new LocationRecord();
        res.user_id = key.getLong();
        res.x = value.getInt();
        res.y = value.getInt();
        res.z = value.getInt();
        res.time_stamp_in_ms = value.getLong();

        out.collect(res);
    }

    @Override
    public ProducerRecord<byte[], byte[]> serialize(LocationRecord pulseRecord, KafkaSinkContext kafkaSinkContext, Long aLong) {
        var key_bytes = ByteBuffer.allocate(8).putLong(pulseRecord.user_id).array();
        var val_bytes = ByteBuffer.allocate(4)
                .putInt(pulseRecord.x)
                .putInt(pulseRecord.y)
                .putInt(pulseRecord.z)
                .putLong(pulseRecord.time_stamp_in_ms)
                .array();

        return new ProducerRecord<>("", key_bytes, val_bytes);
    }
}
```

Далее описывается структура ``DataStream``, описывающая, как будет формироваться поток данных из указанного источника. Данные могут быть распределены по ключам, обработаны в виде окна (прыгающего временного, скользящего временного, прыгающего количественного или скользящего количественного). После этого для перераспределенных (или оставленных без изменения) данных применяется функция, формирующая окончательный поток данных. В приведенном ниже примере это аггергирующая функция, подсчитывающая среднее для элементов, попадающих в окно.

```
DataStream<AverageSpeedVectorRecord> average_speed_vector_stream = env.fromSource(location_source, WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(20)), "location")
				.returns(LocationRecord.class)
				.keyBy(LocationRecord::getUserId)
				.window(SlidingProcessingTimeWindows.of(Duration.ofSeconds(10), Duration.ofSeconds(1)))
				.aggregate(new AverageSpeedAggregate());
```

В данном случае выходные данные должны помещаться снова в топики Kafka, на это раз предназначенные для хранения результатов потоковой обработки. Для этого описывается структура ``KafkaSink``, содержащая информацию о топике назначения и способе сериализации объекта в байты для отправки.

```
		KafkaSink<AverageSpeedVectorRecord> average_speed_sink = KafkaSink.<AverageSpeedVectorRecord>builder()
				.setBootstrapServers("127.0.0.1:9092")
				.setRecordSerializer(new AverageSpeedVectorRecord())
				.setDeliveryGuarantee(DeliveryGuarantee.NONE)
				.build();

		average_speed_vector_stream.sinkTo(average_speed_sink);
```

Результаты анализа исходных данных сохраняются в четыре различных топика:
- **pulse_for_10min** - содержит средний пульс пользователя за последние 10 минут.
- **average_speed_vector** - содержит нормализованный вектор скорости пользователя по осям за последние 2 минуты.
- **motion_point** - содержит выборочные точки маршрута пользователя.
- **most_filled_sectors** - содержит информацию о наиболее загруженных районах карты: их координаты x и y и количество зафиксированных в этом квадрате за 20 секунд сообщений.

Вычисление первых трех характеристик не представляет особой сложности. Для поиска самых загруженных секторов потребовалось перенаправление потока данных. Для этого в качестве ключевой информации берется не Id пользователя, а Id квадрата, в котором находится пользователь. Таким образом, поток преобразуется в пары, первым элементом которых является Id сектора, а вторым - единица. Далее этот поток ограничивается скользящим окном, в рамках которого происходит суммирование единиц по каждому Id квадрата. В результате этого получается поток пар, первым элементом которых является Id квадрата, а вторым - количество пользователей в нем.

```
DataStream<String> sector_fullness_stream = env.fromSource(location_source, WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(20)), "location")
				.returns(LocationRecord.class)
				.map(new MapFunction<LocationRecord, Tuple2<Long, Long>>() {
					@Override
					public Tuple2<Long, Long> map(LocationRecord value) throws Exception {
						return new Tuple2<Long, Long>(value.getSectorId(), 1L);
					}
				})
				.keyBy(t -> t.f0)
				.window(SlidingProcessingTimeWindows.of(Duration.ofSeconds(5), Duration.ofSeconds(5)))
				.sum(1)
				.process(new SectorsProcessor());
```

Далее следовало разработать композицию структур данных, которая бы поддерживала актуальную информацию о наиболее загруженном подмножестве из всех секторов на карте при частом обновлении информации о том или ином секторе. Поскольку реализация очереди с приоритетами в Java не гарантирует логариямического времени при удалении ключа и его значения и добавлении этого же ключа с новым значением, этот функционал потребуется реализовать самостоятельно. Поскольку параметром ранжирования секторов является их загруженность, будет поддерживаться ``TreeSet<Long> SectorsSet``, содержащий все имеющиеся на данный момент различные значения заполненности. Каждой из этих заполненностей с помощью ``HashMap<Long, HashSet<Long>> fullnessToSectorsMap`` ставится в соответствие ``HashSet``, содержащий Id всех имеющих такую загруженность квадратов. Таким образом поддерживается связь между значением заполненности и Id соответствующих секторов. Обратная связь понадобится, когда при поступлении новой или обновленной информации о секторе, можно было за константное время понять, из какого ``HashSet`` удалять информацию об устаревшем значении для этого квадрата. Эта связь реализуется с помощью ``HashMap<Long, Long> sectorToFullnessMap``.


```
	public static class SectorsFullnessComparator implements Comparator<Long> {
		@Override
		public int compare(Long sec1, Long sec2) {
			int value = sec1.compareTo(sec2);
      return Integer.compare(value, 0);
		}
	}

	public static class SectorsProcessor extends ProcessFunction<Tuple2<Long, Long>, String> {
		static TreeSet<Long> SectorsSet = new TreeSet<>(new SectorsFullnessComparator());
		static HashMap<Long, HashSet<Long>> fullnessToSectorsMap = new HashMap<>();
		static HashMap<Long, Long> sectorToFullnessMap = new HashMap<>();
		static long current_number_of_stored_sectors = 0;

```

Полный код функции, обрабатывающей новую запись о некотором секторе, приведен ниже.

```
			if (sectorToFullnessMap.containsKey(sector.f0)) {
				fullnessToSectorsMap.get(sectorToFullnessMap.get(sector.f0)).remove(sector.f0);

				if (fullnessToSectorsMap.get(sectorToFullnessMap.get(sector.f0)).isEmpty()) {
					fullnessToSectorsMap.remove(sectorToFullnessMap.get(sector.f0));
					SectorsSet.remove(sectorToFullnessMap.get(sector.f0));
				}

				sectorToFullnessMap.remove(sector.f0);
				current_number_of_stored_sectors--;
			}

			if (current_number_of_stored_sectors == max_number_of_sectors) {
				var minFullness = SectorsSet.first();

				if (minFullness <= sector.f1) {
					var sectorToRemove = fullnessToSectorsMap.get(minFullness).iterator().next();
					fullnessToSectorsMap.get(minFullness).remove(sectorToRemove);
					sectorToFullnessMap.remove(sectorToRemove);
					current_number_of_stored_sectors--;

					if (fullnessToSectorsMap.get(minFullness).isEmpty()) {
						fullnessToSectorsMap.remove(minFullness);
						SectorsSet.remove(minFullness);
					}
				}
			}

			if (current_number_of_stored_sectors < max_number_of_sectors) {
				sectorToFullnessMap.put(sector.f0, sector.f1);

				if (fullnessToSectorsMap.containsKey(sector.f1) == false) {
					fullnessToSectorsMap.put(sector.f1, new HashSet<>());
					SectorsSet.add(sector.f1);
				}

				fullnessToSectorsMap.get(sector.f1).add(sector.f0);
				current_number_of_stored_sectors++;
			}
		}
```

## Потоковое API и клиентское приложение 
Клиентское и серверное приложения являются, соответственно, последним и предпоследним звеньями цепочки подсистем общей информационной системы, разрабатываемой в рамках курсового проекта. Приложение-сервер осуществляет чтение данных из топиков Kafka и отправку их содержимого по сети приложениям клиентов. Клиентское приложение должно реализовывать получение соответствующих сообщений и реакцию на них в виде отображения изменений в GUI.

На текущем этапе серверное приложение осуществляет чтение из двух топиков Kafka: ``most_filled_sectors``, содержащего информацию о наиболее загруженных районах карты, и ``motion_point``, содержащего агрегированные точки маршрута пользователей. Список загруженных районов является одинаковым для всех пользователей, поэтому рассылается всем подключенным клиентам. Персональные точки маршрута отправляются каждому подключенному пользователю индивидуально. 

Формат взаимодействия является следующим: 
- **Загруженные районы.** Клиентское приложение при запуске отправляет в соответствующую службу одно пустое собщение, чтобы инициировать канал связи, после чего получает поток данных о районах;
- **Точки маршрута.** Клиентское приложение при вводе ID пользователя отправляет в соответствующую службу одно пустое собщение, чтобы инициировать канал связи, после чего получает поток данных о точках маршрута пользователя;

Клиентское приложение должно потокобезопасно в асинхронном режиме получать сообщения, содержащие информацию о наиболее загруженных районах карты, из сети и вносить изменения в соответствии с полученной информацией в GUI, получать сообщения, содержащие агрегированные точки маршрута пользователя, из сети и вносить изменения в соответствии с полученной информацией в GUI.

### Описание в .proto файле содержимого передаваемых сообщений и службы, в рамках которых происходит сетевое взаимодействие
Помимо двух описанных ранее топиков для чтения доступны еще два - топик с информацией о пульсе пользователя и с информацией о векторе скорости пользователя. Разработка служб для них не была осуществлена, но, в образовательных целях для них были сгенерированы службы и сообщения.

С учетом приведенных в предыдущем разделе размышлений, описание создаваемых служб и сообщений в формате .proto для дальнейшей кодогенерации примет вид:

```
service UsersTrackerService {
  rpc getUserPositions (UserID) returns (stream Position);
  rpc getMostFilledSectors (UserID) returns (stream MostFilledSectors);
}

message UserID {
  int64 id = 1;
}

message Position {
  int32 x = 1;
  int32 y = 2;
}

message MostFilledSectors {
  repeated Sector sectors = 1;
}

message Sector {
  int32 x = 1;
  int32 y = 2;
  int64 messages_got = 3;
}
```

Сообщение о наиболее загруженных районах представляет собой массив квадратов, каждый из которых кодируется как координаты x, y и количество сообщений от пользователей, находящихся в этом квадрате. Так как выходные данные служб имеют вид потока, их описание сопровождается словом ``stream``.

### Реализация собственной логики работы служб
Описание типов входных и выходных данных служб позволяет сгенерировать инфтерфейсные методы, но для отражения пользовательской логики функционал необходимо реализовывать самостоятельно.


Поскольку данные о наиболее загруженных районах должны рассылаться всем пользователям, будет логично помещать их в общую очередь, к которой потоки, обслуживающие клиентские подключения, будут обращаться конкурентно, проверяя, является ли первый на выход элемент очереди новым, или он уже был обработан этим потоком.

```
    public void getMostFilledSectors(UserID request, StreamObserver<MostFilledSectors> responseObserver) {
        long lastProcessedTimestamp = 0;
        while (true) {
            var currentMostFilledSectors = mostFilledSectorsQueueLink.peek();

            if (currentMostFilledSectors != null) {
                if (currentMostFilledSectors.timestamp() > lastProcessedTimestamp) {
                    lastProcessedTimestamp = currentMostFilledSectors.timestamp();
                    var sectors = new ArrayList<Sector>();

                    for (int i = 0; i < currentMostFilledSectors.value().y.size(); i++) {
                        sectors.add(Sector.newBuilder()
                                .setX(currentMostFilledSectors.value().x.get(i))
                                .setY(currentMostFilledSectors.value().y.get(i))
                                .setMessagesGot(currentMostFilledSectors.value().number.get(i)).build());
                    }
                    var res = MostFilledSectors.newBuilder().addAllSectors(sectors).build();
                    responseObserver.onNext(res);
                }
            }
        }
    }
```

Данные о точках маршрута конкретного пользователя важны только для потока, обслуживающего подключение этого пользователя, поэтому нет нужды сохранять их в общей очереди. 

```
    public void getUserPositions(UserID request, StreamObserver<Position> responseObserver) {
        motionPointRecordQueuesLink.putIfAbsent(request.getId(), new ConcurrentLinkedQueue<>());

        while (true) {
            var motionPointRecord = motionPointRecordQueuesLink.get(request.getId()).poll();

            if (motionPointRecord != null) {
                var res = Position.newBuilder().setX(motionPointRecord.x).setY(motionPointRecord.y).build();

                responseObserver.onNext(res);
            }

            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        }
    }
```

### Аспект конкурентности
Этот подраздел посвящен разработке кода, обеспечивающего безопасную многопточную работу сервера потового API и клиентского приложения.

Отдельно запускаемые задачи в серверной части:
- Считывание сообщений из топика ``most_filled_sectors``, содержащего информацию о наиболее загруженных районах карты;
- Отправка всем подключенным пользователям общего для всех списка загруженных районов;
- Считывание сообщений из топика ``motion_point``, содержащего агрегированные точки маршрута пользователей;
- Отправка каждому подключенному пользователю его персональных точек маршрута.

Отдельно запускаемые задачи в клиентской части:
- Считывание сообщений, содержащих информацию о наиболее загруженных районах карты, из сети и внесение изменений в соответствии с полученной информацией в GUI;
- Считывание сообщений, содержащих агрегированные точки маршрута пользователя, из сети и внесение изменений в соответствии с полученной информацией в GUI;
- Реагирующий на ввод информации пользователем GUI.

Как было отмечено ранее, поскольку данные о наиболее загруженных районах должны рассылаться всем пользователям, будет логично помещать их в общую очередь, к которой потоки, обслуживающие клиентские подключения, будут обращаться конкурентно, проверяя, является ли первый на выход элемент очереди новым, или он уже был обработан этим потоком.

Данные о точках маршрута конкретного пользователя важны только для потока, обслуживающего подключение этого пользователя, поэтому нет нужды сохранять их в общей очереди. Однако каждая из этих очередей по-прежнему должна быть потокобезопасной, так как поток, наполняющий очереди и поток, считывающий элементы из очереди обращаются к очереди конкурентно. Также, с учетом эксклюзивного владения очередью конкретным подключением, последний считанный элемент можно извлекать сразу, так как никакому другому подключению этот элемент более не понадобится. Сами очереди также должны храниться в структуре данных, допускающей конкурентный доступ, так как при хранении очередей, например, в обычной ``HashMap``, при добавлении новых подключений возможна реаллокация содержимого таблицы, что приведет к инвалидации ссылок на очереди других подключений, которые могут использоваться другими подключениями. Таким образом, очереди для подключений будут храниться в потокобезопасной хэш-таблице.

В качестве очереди с наиболее загруженными районами была использована ``ConcurrentLinkedQueue<ConsumerRecord<String, UsersTrackerService.MostFilledSectorsRecord>>``, а в качестве хэштаблицы - ``ConcurrentHashMap<Long, ConcurrentLinkedQueue<UsersTrackerService.MotionPointRecord>>``, 


Поскольку данные о наиболее загруженных районах и данные о точках маршрута приходят в клиентское приложение в разных потоках, а каждое из этих событий провоцирует перерисовку отдельных компонентов GUI, данные, используемые при перерисовке, и процедура, реализующая перерисовку должны быть потокобезопасными. На основании этих доводов был реализован класс ``SharedResourses``, в массивах ``pointsX`` и ``pointsY`` хранящий координаты точек маршрута, в поле ``sectors`` - текущий список наиболее загруженных районов, в поле ``canvas`` - объект для рисования примитивов, в поле ``useridTextField`` - объект для ввода пользователем его ``user_id``, а в поле ``JTable topSectors`` - объект таблицы, отображающей в GUI информацию о загруженности районов. Для реализации корректного конкурентного доступа к структуре данных потоков, обрабатывающих точки маршрута и список секторов, тела соответствующих методов ``processUserPositions`` и ``processMostFilledSectors`` были защищены общей блокировкой. Внтури обоих методов (и только там) вызывается процедура ``repaint()``, перерисовывающая графическую область и таблицу.
